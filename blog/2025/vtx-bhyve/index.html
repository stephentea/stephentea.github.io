Writing a Hypervisor from Scratch - Software

Created on August 15, 2025

2025   ·   virtualization   operating-systems   ·   systems

This is the second post in my series exploring how to write a hypervisor from scratch. In the first post of the series, we motivated virtualization and took a look at the modern hardware virtualization support (specifically Intel VT-x). In this post, I will explore the design details and walk through the code of BHyVe, which is a hypervisor for FreeBSD.

Again, this post will largely follow ハイパーバイザの作り方, a Japanese blog series on hypervisor development, but I will supplement these notes with my own experience working on BitVisor, a lightweight, para-passthrough hypervisor supporting MacOS, Windows, and Linux, running on top of both Intel and AMD CPUs.

What is BHyVe?

BHyVe is a hypervisor for FreeBSD which started development in 2011. It consists of a kernel module vmm.ko which executes instructions closer to harder (for example, issuing VT-x instructions and modifying VMCS) and a set of userspace programs for emulating hardware, allowing users to launch/shutdown/destroy VMs, etc. This structure is similar to QEMU/KVM for Linux.

Userspace programs mainly consist of three components: (1) /usr/sbin/bhyve performs CPU + hardware emulation, including emulation of virtio-pci, virtio-net, and virtio-blk (2) usr/sbin/bhyveload loads the OS image of a guest VM into the guest memory region, and (3) /usr/sbin/bhyvectl provides an interface for users to manage their VM instances. These userspace programs interface with vmm.ko via libvmmapi, which issues commands to vmm.ko via mmap and ioctl. A high-level system diagram is shown below.

High-level architecture diagram of BHyVe.

Control Loop

Let’s first start with the main control loop of running a VM instance. To initialize a VM instance, usr/sbin/bhyveload creates a device file in /dev/vmm/, and uses this device file to issue commands to vmm.ko to load the guest OS image into memory, initialize registers, set GDT/IDT, etc. Note that this article assumes that BHyVe does not support BIOS/UEFI, but this has been implemented in recent versions of BHyVe. Refer to this section for a detailed explanation of loading + initializing guest VMs.

After usr/sbin/bhyveload finishes initialization, usr/sbin/bhyve will open this /dev/vmm/ file, initialize device emulators, spin up one thread for each vCPU, and issue ioctl(VM_RUN) to vmm.ko. vmm.ko will then perform VMENTRY to switch the CPU to non-root mode. Once a VMEXIT happens, vmm.ko will either handle the event internally, or return to usr/sbin/bhyve via ioctl if necessary (for instance, device emulation is required).

Main control loop of BHyVe.

Now, let’s take a look at the source code for usr/sbin/bhyve, libvmmapi, vmm.ko, and device emulation.

In (9), we set up the vmexit struct to allow the guest to resume execution at the desired location upon a VMEXIT. In (10), we spin up a thread to begin emulation of the vCPU. Let’s look at the function fbsdrun_start_thread:

static void *
fbsdrun_start_thread(void *param)
{
  char tname[MAXCOMLEN + 1];
  struct mt_vmm_info *mtp;
  int vcpu;
  mtp = param;
  vcpu = mtp->mt_vcpu;

  return (NULL);

This function sets the name for the vCPU and begins the main control loop vm_loop in (11). Note that vm_loop is a while (1) loop, hence this function will never return. Let’s take a look at vm_loop:

static vmexit_handler_t handler[VM_EXITCODE_MAX] = {

  [VM_EXITCODE_MTRAP] = vmexit_mtrap,

static void
vm_loop(struct vmctx *ctx, int vcpu, uint64_t rip)
{
  int error, rc, prevcpu;
  if (guest_vcpu_mux)
    setup_timeslice();
  if (pincpu >= 0) {
    error = vm_set_pinning(ctx, vcpu, pincpu + vcpu);
    assert(error == 0);
  }
  while (1) {
    error = vm_run(ctx, vcpu, rip, &vmexit[vcpu]);  // (12)
    if (error != 0) {
      /*
      * It is possible that 'vmmctl' or some other process
      * has transitioned the vcpu to CANNOT_RUN state right
      * before we tried to transition it to RUNNING.
      * This is expected to be temporary so just retry.
      */
      if (errno == EBUSY)
        continue;
      else
        break;
    }
    prevcpu = vcpu;
    rc = (*handler[vmexit[vcpu].exitcode])(ctx, &vmexit[vcpu], &vcpu);  // (13)
    switch (rc) { (23)
      case VMEXIT_SWITCH:  // (14) 
        assert(guest_vcpu_mux);
        if (vcpu == -1) {
          stats.cpu_switch_rotate++;
          vcpu = fbsdrun_get_next_cpu(prevcpu);
        } else {
          stats.cpu_switch_direct++;
        }
      case VMEXIT_CONTINUE:  // (15)
        rip = vmexit[vcpu].rip + vmexit[vcpu].inst_length;
        break;
      case VMEXIT_RESTART:   // (16)
        rip = vmexit[vcpu].rip;
        break;
      case VMEXIT_RESET:     // (17)
        exit(0);
      default:
        exit(1);
    }
  }
  fprintf(stderr, "vm_run error %d, errno %d\n", error, errno);
}

In (12), /usr/sbin/bhyve calls vm_run, which is an API provided by libvmmapi library to issue ioctl to vmm.ko. Once vmm.ko returns (for instance, device emulation is needed), this program invokes the correct handler based on exitcode field of vmexit struct. The program then either switches to a different vCPU (14), continues execution of the next guest instruction (15), reruns the current guest instruction (16), or exits vCPU emulation (17).

libvmmapi

Let’s take a look at the different API functions that libvmmapi provides to userspace programs for interfacing with vmm.ko.

(1) is the struct vm_ops used to store operations for Intel VMX, including vmx_vminit and vmx_run. (2) is used to set the VMCS. Note that the host RIP is set as vmx_longjmp, i.e. on every VMEXIT vmx_longjmp will be called.

For vmx_run, in (3) the function will set the host CR3 and guest RIP. In (4), vmm.ko will handle VMEXITs internally, unless userspace emulation is required. In (5), the function will call vmx_setjmp which is mainly written in assembly to save host registers and other host state. On a VMEXIT, vmx_longjmp will return to the instruction after vmx_setjmp (similar to setjmp and longjmp in C). Depending on whether VMENTRY occurs for the first time or not, either vmx_launch (6) or vmx_resume (7) is called.

ENTRY(vmx_launch)

  VMX_CHECK_AST
  VMX_GUEST_RESTORE 
  vmlaunch

  VM_INSTRUCTION_ERROR(%eax)
  movq %rsp,%rdi

These are some x86 assembly functions for performing saving/restoring of host/guest registers and issuing VT-x instructions. In vmx_setjmp, we save the host registers into vmxctx that are not automatically saved by VMCS. In vmx_launch, we first disable interrupts, restore guest state not automatically restored by VMCS (using a helper macro), then issue VMLAUNCH instruction. If VMLAUNCH fails, we record the failure information and call vmx_return. Otherwise, upon a VMEXIT, vmx_longjmp will be called. We show vmx_return and vmx_longjmp next.

vmx_return restores host state from vmxctx struct, then returns to the instruction after vmx_setjmp (observe that vmx_setjmp saves %RAX into %RSP, which vmx_return restores, places on the stack, and executes ret). vmx_longjmp saves guest registers, then calls vmx_return, which returns to the instruction after vmx_setjmp. If vmx_setjmp returns normally, the return value (held in %RSI) is 0, but if vmx_setjmp returns through vmx_longjmp, the return value is 1 (which is the value of $VMX_RETURN_LONGJMP).

We now return to vmx_run. Previously, we only showed the case when vmx_setjmp returned normally, that is, vmm.ko is about to VMENTER. Now, we show the case when vmx_setjmp returns via vmx_longjmp, i.e. we return to vmm.ko via VMEXIT, and now vmm.ko must perform the necessary handling or return to userspace if necessary.

    vmx_exit_trace(vmx, vcpu, rip, exit_reason, handled);
  } while (handled);
  return (0);
}

In (8), we enable interrupts. In (9), we save information about the VMEXIT. In (10), we call vmx_exit_process, which sets handled to 1 iff vmm.ko is able to handle everything internally. Otherwise, we break out of the loop and return back to userspace (i.e. ioctl returns). Next, we look at the function vmx_exit_process, specifically the case when the guest VM has performed I/O and device emulation, i.e. handled = 0:

static int
vmx_exit_process(struct vmx *vmx, int vcpu, struct vm_exit *vmexit)
{
  int error, handled;
  struct vmcs *vmcs;
  struct vmxctx *vmxctx;
  uint32_t eax, ecx, edx;
  uint64_t qual, gla, gpa, cr3, intr_info;
  vmcs = &vmx->vmcs[vcpu];
  vmxctx = &vmx->ctx[vcpu];
  qual = vmexit->u.vmx.exit_qualification;  // (11)
  vmexit->exitcode = VM_EXITCODE_BOGUS;
  switch (vmexit->u.vmx.exit_reason) {  // (12)
    ...
    case EXIT_REASON_INOUT: 
      /* (13) */
      vmexit->exitcode = VM_EXITCODE_INOUT; 
      vmexit->u.inout.bytes = (qual & 0x7) + 1; 
      vmexit->u.inout.in = (qual & 0x8) ? 1 : 0; 
      vmexit->u.inout.string = (qual & 0x10) ? 1 : 0; 
      vmexit->u.inout.rep = (qual & 0x20) ? 1 : 0; 
      vmexit->u.inout.port = (uint16_t)(qual >> 16); 
      vmexit->u.inout.eax = (uint32_t)(vmxctx->guest_rax); 
      break;
    default:
      break;
  }
  return (handled); 
}

In (11), we get Exit Qualification information (from VMCS). In (12), we switch on Exit Reason. In (13), we save all necessary information in struct vm_exit, including length of access (number of bytes), direction of access, whether the access is a string, whether the access contains a rep-prefix (to indicate number of repetitions of the instruction), and port number. Since device emulation in userspace is necessary, this function does not set handled, i.e. 0 is returned.

Device Emulation

In this section, we look at device emulation in userspace. In the above code snippets, vmm.ko returns from ioctl to vm_run in libvmmapi after a VMEXIT occurs due to the guest VM performing an I/O access. vm_run then returns to vm_loop, which invokes the necessary handler based on the exit code. In this case, the handler vmexit_inout will be invoked, which we show below.

static int
vmexit_inout(struct vmctx *ctx, struct vm_exit *vme, int *pvcpu)
{
  int error;
  int bytes, port, in, out;
  uint32_t eax;
  int vcpu;
  vcpu = *pvcpu;

  /* (1) */
  port = vme->u.inout.port; 
  bytes = vme->u.inout.bytes;
  eax = vme->u.inout.eax;
  in = vme->u.inout.in;
  out = !in;

  error = emulate_inout(ctx, vcpu, in, port, bytes, &eax, strictio);  // (2)
  if (error == 0 && in) 
    error = vm_set_register(ctx, vcpu, VM_REG_GUEST_RAX, eax);  // (3)
  if (error == 0)
    return (VMEXIT_CONTINUE);  // (4)
  else {
    fprintf(stderr, "Unhandled %s%c 0x%04x\n",
    in ? "in" : "out",
    bytes == 1 ? 'b' : (bytes == 2 ? 'w' : 'l'), port);
    return (vmexit_catch_inout());
  }
}

In (1), we get the necessary information for the I/O access. In (2), we call emulate_inout, which performs I/O emulation. If the guest VM performs an in operation, we return the results by setting the guest %RAX register. In (4), we return VMEXIT_CONTINUE to vm_loop, which will resume execution at the next guest instruction. We now look at the function emulate_inout:

int
emulate_inout(struct vmctx *ctx, int vcpu, int in, int port, int bytes,
              uint32_t *eax, int strict)
{
  int flags;
  uint32_t mask;
  inout_func_t handler;
  void *arg;
  assert(port < MAX_IOPORTS);
  handler = inout_handlers[port].handler;  // (5)
  if (strict && handler == default_inout)
    return (-1);
  /* (6) */
  if (!in) {
    switch (bytes) {
      case 1:
        mask = 0xff;
        break;
      case 2:
        mask = 0xffff;
        break;
      default:
        mask = 0xffffffff;
        break;
    }
    *eax = *eax & mask;  // (7)
  }
  flags = inout_handlers[port].flags;
  arg = inout_handlers[port].arg;
  if ((in && (flags & IOPORT_F_IN)) || (!in && (flags & IOPORT_F_OUT)))
    return ((*handler)(ctx, vcpu, in, port, bytes, eax, arg));  // (8)
  else
    return (-1);
}

int
register_inout(struct inout_port *iop)  // (9)
{
  assert(iop->port < MAX_IOPORTS);
  inout_handlers[iop->port].name = iop->name;
  inout_handlers[iop->port].flags = iop->flags;
  inout_handlers[iop->port].handler = iop->handler;
  inout_handlers[iop->port].arg = iop->arg;
  return (0);
}

In (5), we get the registered I/O handler. For guest writes, we set the mask based on length of I/O access in (6) and apply the mask to the value the guest wants to write in (7). In (8), we invoke the handler. We can register an I/O emulation handler using the register_inout function in (9).

We now show examples of device emulation. Our primary focus is on para-virtualized device emulation, which are used due to their high-performance (compared to full-virtualization), but require installing para-virtualized device drivers to the guest OS. Note that more recent developments such as DPDK and SPDK bypass the kernel entirely by performing polling in userspace; this prevents each I/O access from going through 2 stacks: the guest VM and the VMM.

Consport

We end with a simple example of I/O emulation: emulating a paravirtualized console port. This post is getting too long, so I will continue explaining other examples of device emulation (with the main focus being virtio) in the next post in the series!

static void
ttywrite(unsigned char wb)
{
  (void) write(STDOUT_FILENO, &wb, 1);  // (4) 
}

static int
console_handler(struct vmctx *ctx, int vcpu, int in, int port, int bytes,
                uint32_t *eax, void *arg)
{
  static int opened;
  if (bytes == 2 && in) {
    *eax = BVM_CONS_SIG;
    return (0);
  }

  if (bytes != 4)
    return (-1);

  if (!opened) {
    ttyopen();  // (1)
    opened = 1;
  }

  if (in) 
    *eax = ttyread();  // (2)
  else
    ttywrite(*eax);  // (3)
  return (0);
}

static struct inout_port consport = {
  "bvmcons",
  BVM_CONSOLE_PORT,
  IOPORT_F_INOUT,
  console_handler
};

void
init_bvmcons(void)
{
  register_inout(&consport);  // (5)
}

If the console is not open yet, (1) opens it. If the guest attempts to perform a read, console_handler calls ttyread() in (2), otherwise it calls ttywrite() in (3). ttywrite() simply performs a write to STDOUT in (4). This device emulator is registered using register_inout in (5).
