This is the second post in my series exploring how to write a hypervisor from 
scratch.  In the [first post of the series](/blog/2025/vtx-hardware), we motivated 
virtualization and took a look at the modern hardware virtualization support (specifically 
Intel VT-x). In this post, I will explore the design details and walk through the 
code of [BHyVe](https://bhyve.org/), which is a hypervisor for FreeBSD.

Again, this post will largely follow [ハイパーバイザの作り方](https://syuu1228.github.io/howto_implement_hypervisor/), 
a Japanese blog series on hypervisor development, but I will supplement these notes with 
my own experience working on [BitVisor](https://github.com/matsu/bitvisor), a lightweight, 
para-passthrough hypervisor supporting MacOS, Windows, and Linux, running on top of 
both Intel and AMD CPUs.

# What is BHyVe?

BHyVe is a hypervisor for FreeBSD which started development in 2011. It consists 
of a kernel module `vmm.ko` which executes instructions closer to harder (for example, 
issuing VT-x instructions and modifying VMCS) and a set of userspace programs for 
emulating hardware, allowing users to launch/shutdown/destroy VMs, etc. This structure 
is similar to QEMU/KVM for Linux. 

Userspace programs mainly consist of three components: (1) `/usr/sbin/bhyve` performs 
CPU + hardware emulation, including emulation of virtio-pci, virtio-net, and virtio-blk (2) 
`usr/sbin/bhyveload` loads the OS image of a guest VM into the guest memory region, and 
(3) `/usr/sbin/bhyvectl` provides an interface for users to manage their VM instances. 
These userspace programs interface with `vmm.ko` via `libvmmapi`, which issues commands 
to `vmm.ko` via `mmap` and `ioctl`.  A high-level system diagram is shown below.

# Control Loop

Let's first start with the main control loop of running a VM instance. To initialize a VM 
instance, `usr/sbin/bhyveload` creates a device file in `/dev/vmm/`, and uses this device 
file to issue commands to `vmm.ko` to load the guest OS image into memory, initialize registers, 
set GDT/IDT, etc. Note that this article assumes that BHyVe does not support BIOS/UEFI, 
but this has been implemented in recent versions of BHyVe. Refer to [this section](#loading--initializing-guest-vm) for a detailed explanation of loading + initializing guest VMs. 

After `usr/sbin/bhyveload` finishes initialization, `usr/sbin/bhyve` will open this `/dev/vmm/` 
file, initialize device emulators, spin up one thread for each vCPU, and issue `ioctl(VM_RUN)` 
to `vmm.ko`.  `vmm.ko` will then perform VMENTRY to switch the CPU to non-root mode. Once a 
VMEXIT happens, `vmm.ko` will either handle the event internally, or return to `usr/sbin/bhyve` 
via `ioctl` if necessary (for instance, device emulation is required).

In (1), the user passes in the name of the VM instance to start, and this program 
will open the corresponding `/dev/vmm` file. In (2) and (3), guest memory address 
space is mapped to low-memory and high-memory, respectively. In (4), the program 
initializes the emulators for I/O ports, PCI, and I/O APIC. In (5), the program 
obtains the value of guest RIP (instruction pointer).  In (6), the program initializes 
the MP table (needed if more than 1 CPU). In (7), the program initializes ACPI.  
In (8), the program launches the thread corresponding to CPU0 (BSP), passing in 
the guest RIP. 

Now, let's look at the function `fbsdrun_addcpu`:

```c
void
fbsdrun_addcpu(struct vmctx *ctx, int vcpu, uint64_t rip)
{
  int error;
  if (cpumask & (1 << vcpu)) {
    fprintf(stderr, "addcpu: attempting to add existing cpu %d\n", vcpu);
    exit(1);
  }
  cpumask |= 1 << vcpu;
  foundcpus++;

  /* (9) */
  vmexit[vcpu].rip = rip;
  vmexit[vcpu].inst_length = 0;

  if (vcpu == BSP || !guest_vcpu_mux){
    mt_vmm_info[vcpu].mt_ctx = ctx;
    mt_vmm_info[vcpu].mt_vcpu = vcpu;
    error = pthread_create(&mt_vmm_info[vcpu].mt_thr, NULL,  // (10)
                           fbsdrun_start_thread, &mt_vmm_info[vcpu]); 
    assert(error == 0);
  }
}
```
In (9), we set up the `vmexit` struct to allow the guest to resume execution 
at the desired location upon a VMEXIT. In (10), we spin up a thread to begin 
emulation of the vCPU.  Let's look at the function `fbsdrun_start_thread`:

```c
static void *
fbsdrun_start_thread(void *param)
{
  char tname[MAXCOMLEN + 1];
  struct mt_vmm_info *mtp;
  int vcpu;
  mtp = param;
  vcpu = mtp->mt_vcpu;
  snprintf(tname, sizeof(tname), "%s vcpu %d", vmname, vcpu);
  pthread_set_name_np(mtp->mt_thr, tname);
  vm_loop(mtp->mt_ctx, vcpu, vmexit[vcpu].rip);  // (11)
  
  /* will not reach here! */
  exit(1);
  return (NULL);
}
```
This function sets the name for the vCPU and begins the main control loop `vm_loop` in (11). 
Note that `vm_loop` is a `while (1)` loop, hence this function will never return. 
Let's take a look at `vm_loop`:

```c
static vmexit_handler_t handler[VM_EXITCODE_MAX] = {
  [VM_EXITCODE_INOUT] = vmexit_inout,
  [VM_EXITCODE_VMX] = vmexit_vmx,
  [VM_EXITCODE_BOGUS] = vmexit_bogus,
  [VM_EXITCODE_RDMSR] = vmexit_rdmsr,
  [VM_EXITCODE_WRMSR] = vmexit_wrmsr,
  [VM_EXITCODE_MTRAP] = vmexit_mtrap,
  [VM_EXITCODE_PAGING] = vmexit_paging,
  [VM_EXITCODE_SPINUP_AP] = vmexit_spinup_ap,
};

static void
vm_loop(struct vmctx *ctx, int vcpu, uint64_t rip)
{
  int error, rc, prevcpu;
  if (guest_vcpu_mux)
    setup_timeslice();
  if (pincpu >= 0) {
    error = vm_set_pinning(ctx, vcpu, pincpu + vcpu);
    assert(error == 0);
  }
  while (1) {
    error = vm_run(ctx, vcpu, rip, &vmexit[vcpu]);  // (12)
    if (error != 0) {
      /*
      * It is possible that 'vmmctl' or some other process
      * has transitioned the vcpu to CANNOT_RUN state right
      * before we tried to transition it to RUNNING.
      * This is expected to be temporary so just retry.
      */
      if (errno == EBUSY)
        continue;
      else
        break;
    }
    prevcpu = vcpu;
    rc = (*handler[vmexit[vcpu].exitcode])(ctx, &vmexit[vcpu], &vcpu);  // (13)
    switch (rc) { (23)
      case VMEXIT_SWITCH:  // (14) 
        assert(guest_vcpu_mux);
        if (vcpu == -1) {
          stats.cpu_switch_rotate++;
          vcpu = fbsdrun_get_next_cpu(prevcpu);
        } else {
          stats.cpu_switch_direct++;
        }
      case VMEXIT_CONTINUE:  // (15)
        rip = vmexit[vcpu].rip + vmexit[vcpu].inst_length;
        break;
      case VMEXIT_RESTART:   // (16)
        rip = vmexit[vcpu].rip;
        break;
      case VMEXIT_RESET:     // (17)
        exit(0);
      default:
        exit(1);
    }
  }
  fprintf(stderr, "vm_run error %d, errno %d\n", error, errno);
}
```
In (12), `/usr/sbin/bhyve` calls `vm_run`, which is an API provided by `libvmmapi` 
library to issue `ioctl` to `vmm.ko`.  Once `vmm.ko` returns (for instance, device 
emulation is needed), this program invokes the correct handler based on `exitcode` 
field of `vmexit` struct. The program then either switches to a different vCPU (14), 
continues execution of the next guest instruction (15), reruns the current guest 
instruction (16), or exits vCPU emulation (17). 

## `libvmmapi`

Let's take a look at the different API functions that `libvmmapi` provides to 
userspace programs for interfacing with `vmm.ko`.

```c
static int
vm_device_open(const char *name)
{
  int fd, len;
  char *vmfile;
  len = strlen("/dev/vmm/") + strlen(name) + 1;
  vmfile = malloc(len);
  assert(vmfile != NULL);
  snprintf(vmfile, len, "/dev/vmm/%s", name);
  
  fd = open(vmfile, O_RDWR, 0);  // (3)
  free(vmfile);
  return (fd);
}

vm_open(const char *name)
{
  struct vmctx *vm;
  vm = malloc(sizeof(struct vmctx) + strlen(name) + 1);  // (1)
  assert(vm != NULL);
  vm->fd = -1;
  vm->name = (char *)(vm + 1);
  strcpy(vm->name, name);
  if ((vm->fd = vm_device_open(vm->name)) < 0)  // (2)
    goto err;
  return (vm);

err:
  vm_destroy(vm);
  return (NULL);
}
```
In (1) of the code of the [previous section](#usrsbinbhyve), we saw the function 
`vm_open`, which is implemented here. This function allocates a `vmctx` struct in 
(1), and opens the file descriptor in `/dev/vmm` by calling `vm_device_open` in (2). 
`vm_device_open` uses the underlying `open` syscall in (3).

```c

```
In (2) and (3) of the code of the [previous section](#usrsbinbhyve), we saw the 
function `vm_map_memory`, which is implemented here. This function maps the VM 
device file `/dev/vmm` into guest physical address `gpa` using the `mmap` syscall. 

```c

```
In (5) of the code of the [previous section](#usrsbinbhyve), we saw the function 
`vm_get_register`, which is implemented here.  This function is simply a wrapper 
around `ioctl(VM_GET_REGISTER)`, which is a command to `vmm.ko`.  This function 
then takes the return value from `vmm.ko` and sets the `regval` field in `struct vm_register`. 

```c
int
vm_run(struct vmctx *ctx, int vcpu, uint64_t rip, struct vm_exit *vmexit)

  bzero(&vmrun, sizeof(vmrun));
  vmrun.cpuid = vcpu;
  vmrun.rip = rip;

  bcopy(&vmrun.vm_exit, vmexit, sizeof(struct vm_exit));  // (4)
  return (error);

```
In (12) of the code of the [previous section](#usrsbinbhyve), we saw the function 
`vm_run`, which is implemented here. This function is simply a wrapper around `ioctl(VM_RUN)`, 
which starts guest execution at `vmmrun.rip`. If a VMEXIT occurs that `vmm.ko` cannot 
handle by itself, `ioctl` will return with an error code.  This function stores the exit 
information in `vmrun.vm_exit` in (4).

`vmm_dev.c` defines the handlers for various operations on the VM device file in 
`/dev/vmm`, including `open()`, `close()`, `read()`, `write()`, `mmap()`, `ioctl()`. 
The `ioctl()` handler is shown above, which switches on `cmd` and invokes the desired 
function, in this case `vm_run` in response to `VM_RUN`. The function below is used to 
create a new VM instance using `vm_create`. 

```c
static struct vmm_ops *ops;
#define VMINIT(vm) (ops != NULL ? (*ops->vminit)(vm): NULL)
#define VMRUN(vmi, vcpu, rip) (ops != NULL ? (*ops->vmrun)(vmi, vcpu, rip) : ENXIO)

static int
vmm_init(void)
{
  if (vmm_is_intel())
    ops = &vmm_ops_intel;
  else if (vmm_is_amd())
    ops = &vmm_ops_amd;
  return (VMM_INIT());
}

struct vm *
vm_create(const char *name)
{
  vm->cookie = VMINIT(vm);
}

int
vm_run(struct vm *vm, struct vm_run *vmrun)
{
  vcpuid = vmrun->cpuid;
  rip = vmrun->rip;
  error = VMRUN(vm->cookie, vcpuid, rip);
}
```
`vm_create` is a wrapper around the macro `VMINIT`, which invokes the architecture- 
dependent function stored in `struct vm_ops` (for example, there are separate initialization 
functions for VMX and SVM). Similarly, `vm_run` is a wrapper around the macro `VMRUN`. 
Note that `vmm_init` chooses the correct `struct vm_ops` based on the hardware architecture.

```
(1) is the `struct vm_ops` used to store operations for Intel VMX, including 
`vmx_vminit` and `vmx_run`. (2) is used to set the VMCS. Note that the host RIP 
is set as `vmx_longjmp`, i.e. on every VMEXIT `vmx_longjmp` will be called.  

For `vmx_run`, in (3) the function will set the host CR3 and guest RIP. In (4), 
`vmm.ko` will handle VMEXITs internally, unless userspace emulation is required. 
In (5), the function will call `vmx_setjmp` which is mainly written in assembly 
to save host registers and other host state. On a VMEXIT, `vmx_longjmp` will 
return to the instruction after `vmx_setjmp` (similar to `setjmp` and `longjmp` in C).
Depending on whether VMENTRY occurs for the first time or not, either `vmx_launch` (6) 
or `vmx_resume` (7) is called.

This function is used to initialize the VMCS. Note that we must call `VMPTRLD` to 
point the CPU to the VMCS before writing fields (we only show setting the host RIP 
here). We use `VMCLEAR` after modifying the fields to flush the VMCS from cache to 
memory, to ensure that every pCPU has a consistent view of the VMCS in-memory.

These are some x86 assembly functions for performing saving/restoring of host/guest 
registers and issuing VT-x instructions. In `vmx_setjmp`, we save the host registers 
into `vmxctx` that are not automatically saved by VMCS. In `vmx_launch`, we first 
disable interrupts, restore guest state not automatically restored by VMCS (using a 
helper macro), then issue `VMLAUNCH` instruction. If `VMLAUNCH` fails, we record the 
failure information and call `vmx_return`. Otherwise, upon a `VMEXIT`, `vmx_longjmp` 
will be called. We show `vmx_return` and `vmx_longjmp` next.

  movq %rbp,VMXCTX_GUEST_RBP(%rsp)
  movq %r10,VMXCTX_GUEST_R10(%rsp)
  movq %r11,VMXCTX_GUEST_R11(%rsp)
  movq %r12,VMXCTX_GUEST_R12(%rsp)
  movq %r13,VMXCTX_GUEST_R13(%rsp)
  movq %r14,VMXCTX_GUEST_R14(%rsp)
  movq %r15,VMXCTX_GUEST_R15(%rsp)
  movq %cr2,%rdi
  movq %rdi,VMXCTX_GUEST_CR2(%rsp)
  movq %rsp,%rdi
  movq $VMX_RETURN_LONGJMP,%rsi
  addq $VMXCTX_TMPSTKTOP,%rsp
  callq vmx_return
END(vmx_longjmp)
```
`vmx_return` restores host state from `vmxctx` struct, then returns to the 
instruction after `vmx_setjmp` (observe that `vmx_setjmp` saves %RAX into %RSP, 
which `vmx_return` restores, places on the stack, and executes `ret`). `vmx_longjmp` 
saves guest registers, then calls `vmx_return`, which returns to the instruction 
after `vmx_setjmp`.  If `vmx_setjmp` returns normally, the return value (held in %RSI) 
is 0, but if `vmx_setjmp` returns through `vmx_longjmp`, the return value is 1 (which 
is the value of `$VMX_RETURN_LONGJMP`).

We now return to `vmx_run`. Previously, we only showed the case when `vmx_setjmp` 
returned normally, that is, `vmm.ko` is about to VMENTER. Now, we show the case when 
`vmx_setjmp` returns via `vmx_longjmp`, i.e. we return to `vmm.ko` via VMEXIT, and 
now `vmm.ko` must perform the necessary handling or return to userspace if necessary. 

```c
static int
vmx_run(void *arg, int vcpu, register_t rip)
{
  ...
do {
  rc = vmx_setjmp(vmxctx); 
  switch (rc) {
    ...
    case VMX_RETURN_LONGJMP: 
      break;
    }
    enable_intr();  // (8)

    /* (9) */
    vmexit->rip = rip = vmcs_guest_rip(); 
    vmexit->inst_length = vmexit_instruction_length(); 
    vmexit->u.vmx.exit_reason = exit_reason = vmcs_exit_reason(); 
    vmexit->u.vmx.exit_qualification = vmcs_exit_qualification(); 

    handled = vmx_exit_process(vmx, vcpu, vmexit);  // (10)
    vmx_exit_trace(vmx, vcpu, rip, exit_reason, handled);
  } while (handled);
  return (0);
}
```
In (8), we enable interrupts. In (9), we save information about the VMEXIT. 
In (10), we call `vmx_exit_process`, which sets handled to 1 iff `vmm.ko` is 
able to handle everything internally. Otherwise, we break out of the loop and 
return back to userspace (i.e. `ioctl` returns).  Next, we look at the function 
`vmx_exit_process`, specifically the case when the guest VM has performed I/O 
and device emulation, i.e. `handled = 0`:

```c
static int
vmx_exit_process(struct vmx *vmx, int vcpu, struct vm_exit *vmexit)
{
  int error, handled;
  struct vmcs *vmcs;
  struct vmxctx *vmxctx;
  uint32_t eax, ecx, edx;
  uint64_t qual, gla, gpa, cr3, intr_info;
  vmcs = &vmx->vmcs[vcpu];
  vmxctx = &vmx->ctx[vcpu];
  qual = vmexit->u.vmx.exit_qualification;  // (11)
  vmexit->exitcode = VM_EXITCODE_BOGUS;
  switch (vmexit->u.vmx.exit_reason) {  // (12)
    ...
    case EXIT_REASON_INOUT: 
      /* (13) */
      vmexit->exitcode = VM_EXITCODE_INOUT; 
      vmexit->u.inout.bytes = (qual & 0x7) + 1; 
      vmexit->u.inout.in = (qual & 0x8) ? 1 : 0; 
      vmexit->u.inout.string = (qual & 0x10) ? 1 : 0; 
      vmexit->u.inout.rep = (qual & 0x20) ? 1 : 0; 
      vmexit->u.inout.port = (uint16_t)(qual >> 16); 
      vmexit->u.inout.eax = (uint32_t)(vmxctx->guest_rax); 
      break;
    default:
      break;
  }
  return (handled); 
}
```
In (11), we get Exit Qualification information (from VMCS). In (12), we switch on 
Exit Reason. In (13), we save all necessary information in `struct vm_exit`, including 
length of access (number of bytes), direction of access, whether the access is a string, 
whether the access contains a rep-prefix (to indicate number of repetitions of the instruction), 
and port number.  Since device emulation in userspace is necessary, this function does not 
set `handled`, i.e. 0 is returned.

# Device Emulation 
In this section, we look at device emulation in userspace.  In the above code snippets, 
`vmm.ko` returns from `ioctl` to `vm_run` in `libvmmapi` after a VMEXIT occurs due to the guest VM 
performing an I/O access.  `vm_run` then returns to `vm_loop`, which invokes the necessary 
handler based on the exit code. In this case, the handler `vmexit_inout` will be invoked, 
which we show below. 

```c
static int
vmexit_inout(struct vmctx *ctx, struct vm_exit *vme, int *pvcpu)
{
  int error;
  int bytes, port, in, out;
  uint32_t eax;
  int vcpu;
  vcpu = *pvcpu;

  /* (1) */
  port = vme->u.inout.port; 
  bytes = vme->u.inout.bytes;
  eax = vme->u.inout.eax;
  in = vme->u.inout.in;
  out = !in;

  error = emulate_inout(ctx, vcpu, in, port, bytes, &eax, strictio);  // (2)
  if (error == 0 && in) 
    error = vm_set_register(ctx, vcpu, VM_REG_GUEST_RAX, eax);  // (3)
  if (error == 0)
    return (VMEXIT_CONTINUE);  // (4)
  else {
    fprintf(stderr, "Unhandled %s%c 0x%04x\n",
    in ? "in" : "out",
    bytes == 1 ? 'b' : (bytes == 2 ? 'w' : 'l'), port);
    return (vmexit_catch_inout());
  }
}
```
In (1), we get the necessary information for the I/O access. In (2), we call 
`emulate_inout`, which performs I/O emulation.  If the guest VM performs an in 
operation, we return the results by setting the guest %RAX register. In (4), we 
return `VMEXIT_CONTINUE` to `vm_loop`, which will resume execution at the next guest 
instruction. We now look at the function `emulate_inout`:

```c
int
emulate_inout(struct vmctx *ctx, int vcpu, int in, int port, int bytes,
              uint32_t *eax, int strict)
{
  int flags;
  uint32_t mask;
  inout_func_t handler;
  void *arg;
  assert(port < MAX_IOPORTS);
  handler = inout_handlers[port].handler;  // (5)
  if (strict && handler == default_inout)
    return (-1);
  /* (6) */
  if (!in) {
    switch (bytes) {
      case 1:
        mask = 0xff;
        break;
      case 2:
        mask = 0xffff;
        break;
      default:
        mask = 0xffffffff;
        break;
    }
    *eax = *eax & mask;  // (7)
  }
  flags = inout_handlers[port].flags;
  arg = inout_handlers[port].arg;
  if ((in && (flags & IOPORT_F_IN)) || (!in && (flags & IOPORT_F_OUT)))
    return ((*handler)(ctx, vcpu, in, port, bytes, eax, arg));  // (8)
  else
    return (-1);
}

int
register_inout(struct inout_port *iop)  // (9)
{
  assert(iop->port < MAX_IOPORTS);
  inout_handlers[iop->port].name = iop->name;
  inout_handlers[iop->port].flags = iop->flags;
  inout_handlers[iop->port].handler = iop->handler;
  inout_handlers[iop->port].arg = iop->arg;
  return (0);
}
```
In (5), we get the registered I/O handler. For guest writes, we set the mask 
based on length of I/O access in (6) and apply the mask to the value the guest 
wants to write in (7). In (8), we invoke the handler. We can register an I/O 
emulation handler using the `register_inout` function in (9). 

We now show examples of device emulation. Our primary focus is on para-virtualized 
device emulation, which are used due to their high-performance (compared to full-virtualization), 
but require installing para-virtualized device drivers to the guest OS. Note that more recent 
developments such as [DPDK](https://www.dpdk.org/) and [SPDK](https://spdk.io/) bypass the kernel 
entirely by performing polling in userspace; this prevents each I/O access from going through 2 stacks: 
the guest VM and the VMM. 

## Consport
We end with a simple example of I/O emulation: emulating a paravirtualized 
console port. This post is getting too long, so I will continue explaining 
other examples of device emulation (with the main focus being virtio) in the 
next post in the series!

```c
static void
ttywrite(unsigned char wb)
{
  (void) write(STDOUT_FILENO, &wb, 1);  // (4) 
}

static int
console_handler(struct vmctx *ctx, int vcpu, int in, int port, int bytes,
                uint32_t *eax, void *arg)
{
  static int opened;
  if (bytes == 2 && in) {
    *eax = BVM_CONS_SIG;
    return (0);
  }

  if (bytes != 4)
    return (-1);

  if (!opened) {
    ttyopen();  // (1)
    opened = 1;
  }

  if (in) 
    *eax = ttyread();  // (2)
  else
    ttywrite(*eax);  // (3)
  return (0);
}

static struct inout_port consport = {
  "bvmcons",
  BVM_CONSOLE_PORT,
  IOPORT_F_INOUT,
  console_handler
};

void
init_bvmcons(void)
{
  register_inout(&consport);  // (5)
}
```
If the console is not open yet, (1) opens it. If the guest attempts to perform a read,
`console_handler` calls `ttyread()` in (2), otherwise it calls `ttywrite()` in (3). `ttywrite()` 
simply performs a write to STDOUT in (4). This device emulator is registered using 
`register_inout` in (5).
