# Virtio

Virtio is one of the most widely used frameworks for paravirtualization of devices. 
The framework is supported by a wide variety of hypervisors (including KVM, VirtualBox, 
BHyVe, etc.) and operating systems (Linux, FreeBSD, Windows, etc.). Full device emulation 
has a high overhead --- guest drivers often make multiple accesses to hardware registers, 
each of which incurs a cost of VMEXIT → emulation in userspace → VMRESUME. 

On the other hand, virtio enables guest VMs and hypervisors to communicate via ring buffers in 
shared memory.  Guest VMs notify hypervisors of data to be processed in the queue via VMEXIT, 
and hypervisors are able to disable this VMEXIT if they are already currently processing the queue. 
Thus, the number of mode switches is dramatically less compared to full emulation. 

Virtio consists of two components: virtio PCI and virtqueue.  Virtio PCI refers to 
the hypervisor emulating PCI devices for guest VMs. Virtio PCI consists of configuration 
registers, event notifications between hypervisor and guest, and transfer of data via DMA. 
Virtqueue refers to shared circular buffers between the hypervisor and guest (similar to an 
IPC mechanism). For instance, virtio-net (which is used to paravirtualize NICs) consist of 
3 queues: receive (RX) queue, send (TX) queue, and control queue. 

## Virtio PCI

Let's start with virtio PCI.  First, I will explain the basics of PCI devices. 
A PCI device is uniquely identified by the triplet `[bus number : device number . function number]`. 
Each PCI device has a PCI configuration space, PCI I/O space, and PCI memory space. 

PCI configuration space consists of device information such as `[vendor ID : device ID]`, 
pointers to PCI I/O space and PCI memory space, information about MSI interrupts, and 
other information for initializing drivers for this device. To access PCI configuration 
space, the guest VM takes the following steps:

1. Set the `[bus number : device number . function number]`, the offset of access, 
and the enable bit in the CONFIG_ADDRESS register. This is usually mapped at address 
0xCF8 in the I/O address space. 

2. Read or write to CONFIG_DATA register. This is usually mapped at address 0xCFC 
in the I/O address space. 

As part of initialization, the guest VM will iterate through every 
`[bus number : device number . function number]` and read the corresponding 
PCI configuration space to find out which PCI devices are connected to the 
system. 

PCI configuration space contains Base Address Registers that point to PCI I/O space 
and PCI memory space. PCI I/O space is usually mapped to I/O address space (although in 
some architectures, it can be mapped to memory address space) and is used to access hardware registers. 
PCI memory space is mapped to memory address space and used for larger transfers of data via DMA, 
such as video buffers. 

*To learn more about PCI devices, check out [this blog post]() I wrote about 
Intel VT-d, which covers virtualization support for DMA from PCI devices. [This paper]() 
is also a valuable read for those looking to learn more about the internals of PCIe devices 
and benchmarking their performance.*

To virtualize PCI devices, the hypervisor shadows these PCI spaces. Virtio devices 
have `vendor ID = 0x1AF4`, `device ID = 0x1000 - 0x1040` in the PCI configuration space. 
The hypervisor uses the Subsystem Device ID to specify the type of virtio device. In 
addition, the hypervisor places a virtio header in the PCI I/O space to allow for further 
configuration between the hypervisor and guest VM.  Fields in the virtio header are shown 
below.

The guest VM discovers and initializes a virtio device driver as follows:

1. Discover the `[vendor ID : device ID]` of a virtio device while iterating through 
`[bus number : device number . function number]` and reading the corresponding 
PCI configuration space.

2. Set the STATUS field of virtio header in PCI I/O space to ACKNOWLEDGE. 

3. Use the Subsystem Device ID to determine which virtio device driver to load. 
For instance, if the Subsystem Device ID is 1, the guest VM loads a virtio-net 
driver. If the Subsystem Device ID is 2, the guest VM loads a virtio-blk driver. 

4. After loading the driver, set the STATUS field of virtio header in PCI I/O space 
to DRIVER. 

5. Perform device-specific initialization. For instance, for virtio-net, the guest 
VM will copy the MAC address from virtio header and register the virtual NIC into the 
network subsystem. The guest VM will read the HOST_FEATURES field to discover which 
features are available, and set the bits in the GUEST_FEATURES field to indicate which 
features it wishes to use. For instance, the guest VM may request checksum offloading 
or TSO (TCP Segmentation Offload). 

6. Allocate the necessary queues (more on this below). 

7. Once driver initialization is complete, set the STATUS field of virtio header in 
PCI I/O space to DRIVER_OK. If a failure occurs during driver initialization, set the 
field to FAILED. 

The guest VM will allocate the necessary queues for virtqueue using the following steps. 
These steps are repeated for every queue the guest VM wants to use (for instance, virtio-net 
requires 3 queues as explained above).

1. Write the queue number to QUEUE_SEL to virtio header. 

2. Read the QUEUE_NUM from virtio header to determine the length of the queue 
specified by QUEUE_SEL. If QUEUE_NUM is 0, the hypervisor does not allow the 
guest VM to use this queue. 

3. Allocate the queue with size specified by QUEUE_NUM. The base address of the queue 
must be page-aligned.

4. Write the page frame number (PFN) of the base address of the queue to QUEUE_PFN in 
virtio header. 

5. If the device supports MSI (read the PCI configuration space), write to either the 
MSI_CONFIG_VECTOR or MSI_QUEUE_VECTOR field in virtio header, depending on whether the 
queue is for control or not.
